# ADB 진입과 USB 연결

## 무엇까지 확인했나

| 항목 | 근거 및 한계 |
| --- | --- |
| ADB 연결·앱 설치 | JSN 국내 사양, API 17, `eng.vmadmin.20250902.081552`에서 성공 |
| 숨은 메뉴·연도별 암호·Factory Test 명령 | 다운로드본 260114의 코드 경로 분석. 모든 실차 버전에서 같은 화면·암호라고 확인한 것은 아님 |
| USB 디버깅 상태 변경 | OEM `MiscManager.setSystem(5/6)` 경로 확인. 설정 ON만으로 케이블 연결 성공을 뜻하지 않음 |
| 케이블 | 케이블 교체 후 성공 이력 있음. 범용 구매 모델·전기 배선까지 검증한 자료는 없음 |

차량을 정차하고 화면을 확인할 수 있을 때 진행합니다. 설치에 Variant Coding, CPU Variant Coding, 펌웨어 업데이트, 공장 초기화는 필요하지 않습니다.

## 1. 최초 진입 후보: 엔지니어링 모드

다운로드본 260114에서 확인한 진입 경로입니다. 실제 화면이 다르면 좌표를 추측해 다른 메뉴를 누르지 마세요.

1. 설정의 **SW 정보/업데이트** 화면으로 이동합니다.
2. 하단 업데이트 버튼 줄의 **왼쪽 숨은 영역 5회 → 오른쪽 숨은 영역 1회**를 첫 터치부터 10초 안에 누릅니다. 길게 누르는 동작이 아닙니다.
3. 영역은 코드상 양 끝 컨테이너의 아래에 있는 60×60dp 터치 뷰입니다. 화면 전체 모서리라고 단정할 수 없으며 실차 픽셀 좌표는 미확정입니다. 실패하면 10초 이상 기다려 초기화한 뒤 시도합니다. 왼쪽 10회·15회에는 별도 동작이 있으므로 횟수를 늘리지 않습니다.
4. 암호는 업데이트 파일 날짜가 아니라 **장치 달력 연도**에 따라 선택됩니다. 분석본의 후보는 **2026년 `0567`, 2027년 `1278`**입니다. 장치 날짜·버전이 다르거나 시간 미설정이면 같다고 보장할 수 없습니다. 이 암호 자체의 실차 성공을 별도 기록으로 확인한 것은 아닙니다.

코드상 `SystemInfo`의 클릭 처리에서 `InputPasswordExt`를 열고, `getKeyString`에서 `Calendar.YEAR`를 참조합니다. OEM 코드 원문은 배포하지 않습니다.

## 2. Factory Test에서 USB debug 요청

메뉴가 존재하는 경우 **Diagnosis → Factory Test**로 이동합니다. `DTC for developer`와 다릅니다. 다음은 분석본의 `sendCmd` 경로로 확인한 입력 형식입니다.

| 순서 | 입력창에 넣을 문자열 | 동작 |
| --- | --- | --- |
| 1 | `0A 01` | 입력 후 SEND: factory mode 진입 |
| 2 | `65 01` | 앞 내용을 지우고 입력 후 SEND: USB debug 요청 |
| 3 | `0A 02` | 앞 내용을 지우고 입력 후 SEND: factory mode 종료 |

**각 줄은 두 개의 16진수 바이트를 공백 한 칸으로 구분**합니다. `6501`, `0A01`, 여러 줄 한 번 전송, 한 바이트씩 SEND가 아닙니다. 분석본에서 `65` 처리는 factory mode 상태를 요구하며, 종료 처리에는 USB 상태를 되돌리는 코드가 없습니다. 이 경로의 존재와 실제 PC USB 열거 성공은 별도 단계입니다.

필요 시 같은 경로에서 일반 USB 상태로 요청하는 순서는 `0A 01` SEND → `65 00` SEND → `0A 02` SEND입니다. 다른 번호를 탐색하거나 반복 전송하는 절차는 제공하지 않습니다.

이미 ‘내 앱’을 설치했다면 **내 앱 → USB 디버깅 → ON**을 사용할 수 있습니다. 다시 열어 `설정: ON`을 확인해도 이는 요청된 설정 상태이며 물리 연결 확인은 아닙니다. 처음 앱을 설치하기 전에는 이 버튼을 사용할 수 없습니다.

## 3. PC에서 USB 열거와 ADB를 따로 확인

공식 [Android SDK Platform-Tools](https://developer.android.com/tools/releases/platform-tools)를 준비합니다. 아래 명령은 PC에서 실행합니다. ADB의 장치 선택과 상태는 [공식 ADB 문서](https://developer.android.com/tools/adb)를 참고하세요.

```sh
adb devices -l
# macOS에서만: USB 장치가 물리적으로 나타나는지 확인
ioreg -p IOUSB -l -w 0
```

성공 사례의 USB 이름은 **Telechips / DiPO**, VID `0x18d1`, PID `0xd00d`입니다. ADB 목록에 나온 본인 기기의 일련번호를 사용하며, 문서의 `YOUR_DEVICE_SERIAL`을 그대로 쓰지 않습니다.

| 상태 | 다음 확인 |
| --- | --- |
| USB 트리에 장치 자체가 없음 | 케이블·포트·데이터 연결·USB 역할과 실제 모드 전환부터 확인. APK 재설치나 ADB 권한 승인은 이 단계의 해결책이 아님 |
| USB에는 있고 ADB에는 없음 | PC의 ADB 서버/드라이버와 해당 인터페이스 확인. PC에서 `adb kill-server`, `adb start-server` 후 재조회 가능 |
| `offline` | 케이블 재연결과 ADB 서버 재시작 후 상태 확인 |
| `unauthorized` | 기기에 승인창이 실제 표시되면 승인. 구형 OEM 빌드에서 승인창이 반드시 나타난다고 가정하지 않음 |
| `device` | 아래 기기 속성을 읽어 대상 확인 후 설치 문서로 이동 |

```sh
VN_SERIAL='YOUR_DEVICE_SERIAL'
adb -s "$VN_SERIAL" shell getprop ro.product.name
adb -s "$VN_SERIAL" shell getprop ro.build.version.sdk
adb -s "$VN_SERIAL" shell getprop ro.build.version.incremental
```

확인 대상은 순서대로 `jsn_kr`, `17`, `eng.vmadmin.20250902.081552`입니다. 구형 adbd에서 `adb shell -T`는 실패했으므로 일반 `adb shell`을 사용합니다.

## 케이블과 되풀이되는 연결 문제

차량 USB-A 암포트와 PC를 연결하는 물리 구성에서 A-A 케이블·어댑터가 사용된 성공 이력은 있으나, 일반 A-C 케이블과 C→A 암 HOST 어댑터 조합은 USB 역할이 같지 않을 수 있습니다. **A-A라는 커넥터 형태만으로 적합성이나 안전성을 보장할 수 없습니다.** 검증된 서비스 연결 구성·배선을 확인해야 하며, 임의 두 호스트의 전원을 연결하거나 선을 잘라 개조하는 방법은 이 안내에 포함하지 않습니다.

성공했던 케이블·어댑터·포트 조합을 유지하고 USB 트리를 확인하세요. ‘충전 중으로 전환되지 않음’ 또는 ‘Mac이 충전됨’은 ADB 연결 증거가 아닙니다. 설정 ON인데도 장치가 없으면 디버깅 OFF → 케이블 분리 → ON → 재연결을 한 차례 확인할 수 있지만, 이것이 어떤 실패든 해결한다는 보장은 없습니다.

## 숨은 ADB 항목의 의미

`com.hkmc.software.engineermode.adb_hide` feature는 이더넷 ADB 탭을 숨기는 조건입니다. WIFI ADB 문자열이 있어도 메인 메뉴에서 화면을 여는 분기는 확인되지 않았습니다. 관련 broadcast는 기기 안에서 실행 중인 송신자가 필요하며, PC에서 Wi-Fi로 직접 보내 최초 진입을 만드는 절차가 아닙니다. Wi-Fi 드라이버·모듈 가용성도 별도 문제입니다.

다운로드본과 실차 빌드가 다르므로, 메뉴·암호·케이블·무선 ADB 중 어느 하나를 모든 차에 통하는 우회 방법으로 취급하지 않습니다.
